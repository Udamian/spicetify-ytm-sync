# Spikes

Short, throwaway experiments that settle risky assumptions *before* the product is built on
them. The reasoning behind each is in [`../docs/roadmap.md`](../docs/roadmap.md#phase-0-spikes).
Record each result in this table (and date it) when you finish.

| Spike | Question | How | Result |
|---|---|---|---|
| **S1** Session durability | How long does a captured session keep working? | [`s1_session_durability.py`](s1_session_durability.py) | _pending_ |
| **S2** Writes | Do `add_playlist_items`, `addToTop` and `moveItem` work with the current `ytmusicapi`? | [`s2_writes.py`](s2_writes.py) (reuses the S1 session; only touches a playlist it creates and deletes) | **Done 2026-10-15 (run 3, call statuses checked).** All steps pass with `SUCCEEDED`: create, search, add (batches of 3, 5, 10, 15; one earlier run also took 30), order preserved with `setVideoId`, `moveItem`, `addToTop`. Findings: (1) ytmusicapi does **not raise** when YouTube refuses a write, it returns the response, so always check the status; (2) `duplicates=False` + any duplicate in the batch -> `STATUS_FAILED`, nothing added; (3) `duplicates=True` adds the duplicate again (7 -> 9), so it does not skip them: **the engine must filter duplicates itself**; (4) reads right after a write can lag (a `moveItem` and a 30-track batch looked failed in run 2 and passed later): verify through the returned status and re-read with retries. _Not covered:_ playlists near 5,000 items. |
| **S3** Localhost from Spicetify | What is the real `location.origin`? Can the web view `fetch` `127.0.0.1`? | Spotify DevTools console | **Done 2026-10-14.** `location.origin` = `https://xpui.app.spotify.com`; plain `fetch` to `127.0.0.1` works; `Authorization` header passes CORS preflight (401 from the companion, not a CORS error). |
| **S4** Reading playlists | Order and date added for 5,000+ tracks (Spicetify APIs only) | Spotify DevTools console | **Partly done 2026-10-14.** `LibraryAPI.getTracks`: `addedAt`, `totalLength`, newest first, 500/page in ~380 ms. `PlaylistAPI.getContents(uri,{limit,offset})`: returns `items`, `totalLength`, `addedAt` per item. _Pending:_ confirm playlist item order equals on-screen order, and 5,000+ pagination. |
| **S5** Matching | Accuracy over 200 of your own tracks | 1) paste [`s5_export.js`](s5_export.js) in the Spotify console and save the clipboard as `spikes/.s1/tracks.json`; 2) `python spikes/s5_matching.py spikes/.s1/tracks.json` (read-only searches); 3) `python spikes/s5_review.py` and check by hand | **Done 2026-10-15, 200 random Liked Songs.** First scoring: 176 ok, 23 review, 1 not_found; manual check: all sampled `ok` and all 23 `review` were correct, the `not_found` is really missing. Cause of the reviews: collaborations (YouTube Music lists fewer artists and puts the rest in the title as `feat. X`, or a different one first). After changing the artist score (any shared artist counts, `feat.` names in the title count) and adding the 'clean match' rule: **198 ok (99 %), 1 review, 1 not_found**; the 22 rows that changed were the ones verified correct. Caveat: one sample of 200 from one library; re-measure in the beta. |
| **S6** Packaging | Does PyInstaller trigger SmartScreen/antivirus on a clean Windows? | Manual | _pending_ |
| **S7** Marketplace manifest | Is one root `manifest.json` enough for a built app? | Manual | _pending_ |
